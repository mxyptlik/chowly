# Chowly Build Brain

This file is the durable coordination memory for the Chowly build. `CONTEXT.md` remains the product/domain authority; `TASKS_TO_DO.md` is the execution authority; this file records the implementation state, assignments, evidence, conflicts, and master audits.

## Product north star

Chowly is a multi-tenant, multi-location restaurant operations platform. V1 is web-first with optional PWA installation and supports three connected experiences: a no-account diner flow, staff operations, and tenant/platform administration. The pilot target is seven independent tenants with one location each, while the architecture must already enforce tenant and location boundaries.

## Decisions that must not drift

- A customer record is required for every order. Name and phone are required, email is optional, and diners do not sign up, sign in, or complete OTP.
- Phone identity is globally unique internally, but each restaurant sees only customer/order data captured through that tenant.
- A table can have multiple simultaneous, separate orders. Orders are not merged by table.
- Daily table QR tokens are durable for that table/day and can be force-regenerated by a waiter or manager. Manual waiter order entry is the fallback.
- Dine-in can become takeaway only before staff acceptance. Diners can self-cancel only before acceptance; later changes require waiter/manager assistance and audit.
- The accepting waiter owns the order. Managers can accept/reassign. Accepted additions become new orders.
- Food and drink lines route independently to kitchen and bar. Chef/bartender claim locks waiter amendments. The diner sees preparing until all active lines are ready; a waiter/manager then serves.
- Payment happens only after service, exactly once and in full per order. V1 uses mock NGN card, bank transfer, and wallet adapters; cash is staff-recorded only. Only a manager can issue one full refund with a reason.
- Digital receipt is primary and can be emailed when optional email exists.
- Item rating is once per food/drink line; overall rating is once per order. Scores 1-2 prompt, but do not force, a complaint. Complaints are manager-only and post-service.
- Reservations are simple requests with explicit staff confirmation; no deposit, waitlist, or automatic allocation.
- Tenant retention defaults to 90 days, can be configured through 120 days, and longer periods require platform approval.
- Required reports: daily orders/revenue/payment/refunds, average wait, top items, cancellations, complaints, and ratings by location/date.
- Stack: FastAPI, SQLAlchemy, Alembic, PostgreSQL, Redis, Dramatiq, WebSockets; Next.js website-first with optional PWA and IndexedDB offline tolerance. Firebase/Supabase and real payment integration are not part of this design.

## Baseline observed before this execution program

The repository already contained a functional prototype happy path: public QR menu/order, global phone-based customer reuse, tax/service totals, waiter acceptance, prep claim/ready, service, mock payment, and table visit closure. A direct backend order-flow test and a Next.js production build had passed previously.

The baseline was not a complete V1. It lacked real staff authentication/RBAC/tenant isolation, Alembic migrations, reservations, complaints/ratings/retention/reporting, most correction operations, robust payments/refunds/receipts, daily QR rotation, WebSockets, offline outbox/conflicts, modifier selection UI, administration screens, and broad accessibility/E2E coverage. Public cash and caller-supplied staff authority were known security defects.

## Architecture direction

```text
Next.js web/PWA
  |-- public diner session: daily QR token + unguessable order access token
  |-- authenticated staff session: tenant + roles + explicit location assignments
  |-- IndexedDB: cached safe reads + restricted pending outbox
  |-- WebSocket live events with polling fallback
  v
FastAPI routers -> authorization dependencies -> domain services
  |                                      |-- append-only audit events
  |                                      |-- post-commit live events
  v                                      v
PostgreSQL (Alembic versioned)       Redis / Dramatiq workers
```

Pricing and status transitions belong in backend domain services. Frontends render server-confirmed state and may show a separate `Pending sync` state, never a fabricated terminal state. Tenant/location predicates and database constraints are defense in depth, not optional UI conventions.

## Dependency and aggregation rules

1. Schema/migrations land before security and all model-dependent domains.
2. Security lands before protected domain APIs.
3. Menu/table/QR and realtime primitives land before the full order lifecycle.
4. Order lifecycle lands before payments and reporting.
5. Shared frontend foundation lands before diner/staff feature paths.
6. Domain agents integrate upward only through committed/shared contracts and targeted tests.
7. The release-verification path aggregates all lower paths, then the master agent runs a separate traceability audit.

## Completion standard

An agent may check a task only when:

- the implementation exists at the named path;
- tests specifically exercise the behavior and its authorization/error cases;
- the targeted test/build command passes;
- any migration, API contract, or user-facing behavior change is documented here;
- no unrelated user change was overwritten.

An agent completes a path by adding an evidence entry below with files, test commands, results, known risks, and the exact checkbox count. The master agent may reopen tasks after integration or security review. Final completion is forbidden until all P00-P13 items are checked and final clean-environment evidence is recorded.

## Interface and migration decisions

Record newly introduced route prefixes, event versions, model constraints, migration revisions, session mechanism, and offline idempotency contract here as paths complete.

- P01 migration contract: canonical initial revision is `48f961b063ff`. Canonical tables use `staff_accounts`, `staff_role_assignments`, `staff_location_assignments`, `table_qr_tokens`, `customer_tenant_records`, `payment_attempts`, `refunds`, and `receipts`; prototype imports `Staff` and `Payment` remain temporary aliases only. `Base.metadata.create_all` is test-only; runtime startup requires `alembic upgrade head`.
- P02 staff auth contract: `POST /api/v1/staff/auth/login`, `POST /logout`, `GET /session`, `POST /refresh`, and `POST /active-location` use the HttpOnly `chowly_staff_session` cookie (`SameSite=Lax`, `/api/v1` path; `Secure` is mandatory outside development). The signed HS256 claims contain only staff ID, tenant ID, active location, issued/expiry times, and a random token ID; roles and location assignments are reloaded and revalidated from SQL on every request. Default lifetime is eight hours and refresh rotates the signed token.
- P02 invitation contract: authenticated tenant owners may invite tenant roles inside their explicit location grants; managers may invite waiter/chef/bartender roles only inside their grants. `POST /api/v1/staff/auth/invitations` returns the raw acceptance token exactly once while SQL stores only SHA-256; `POST /invitations/accept` consumes it once, rejects expiry, and stores only bcrypt password hashes. Delivery UX remains P12 work.
- P02 realtime grant contract: `POST /api/v1/staff/auth/realtime-grant` accepts an assigned `location_id` and one role actually held by the principal, then issues a five-minute P03-compatible token. A platform administrator session does not implicitly grant restaurant-location operations.
- P02 local bootstrap contract: only development/test environments seed `owner@demo.chowly.ng`, `manager@demo.chowly.ng`, `waiter@demo.chowly.ng`, `chef@demo.chowly.ng`, and `bar@demo.chowly.ng` with password `ChowlyDemo!2026`; the password is bcrypt-hashed. Production startup refuses placeholder signing secrets/insecure session cookies and skips deterministic seeding.
- P03 event contract: every application event is a strict `version: "1.0"` envelope with UUID `id`, channel-local monotonic `sequence`, `type`, UTC `occurred_at`, hierarchical `scope`, typed `resource`, and JSON `payload`. Supported types are `order.changed`, `order_line.changed`, `table.changed`, `menu_availability.changed`, `reservation.changed`, `complaint.changed`, `payment.changed`, and `receipt.changed`.
- P03 channel/auth contract: staff connect to `/api/v1/ws/staff/tenants/{tenant_id}/locations/{location_id}?role={ROLE}&token={SIGNED_GRANT}&last_sequence={N}`. The HMAC grant must be unexpired and match tenant, location, and one of the allowed roles; each role has a distinct channel and sequence. Diners connect to `/api/v1/ws/public/orders/{order_id}?access_token={SIGNED_ORDER_GRANT}&last_sequence={N}` and the grant is bound to exactly that order. Invalid/expired grants close 4401; mismatched scope closes 4403.
- P03 replay/liveness contract: Redis Streams retain the last configured 500 messages per channel while Redis pub/sub fans out across API processes. Reconnect with `last_sequence`; clients discard duplicate sequence values and refresh their REST snapshot if they observe a gap. The server sends `system.heartbeat`; clients reply `system.pong`; stale sockets close and are removed. `stage_domain_event` plus `commit_and_publish` guarantees rollback never emits live success.
- P03 job contract: `send_receipt_email` and `cleanup_tenant_retention` use persistent Redis completion markers, concurrent locks, provider-facing idempotency keys, recorded attempts/errors/results, and bounded Dramatiq retry/backoff. Receipt delivery currently uses the explicit console adapter; P06 replaces it with receipt rendering/delivery. Retention orchestration late-binds `app.retention.run_retention_cleanup`, whose data semantics are owned by P08.
- P03 aggregation note: `app.routers.realtime.router` is exported but must be mounted by the application composition path after P02 supplies authenticated grant issuance. P13 must run a live multi-process Redis replay/fanout check; P03 unit tests already prove envelope validation and tenant/location/role/public-order isolation without external services.
- P07 route contract: application composition must mount `app.routers.reservations.router`. Public request is `POST /api/v1/public/reservations`. Assigned-location staff use `GET /api/v1/staff/locations/{location_id}/reservations`, `GET /api/v1/staff/reservations/{reservation_id}`, and `POST /api/v1/staff/reservations/{reservation_id}/{confirm|reject|cancel|seat}`. Confirm accepts an optional table/note; reject and cancel require a reason; seat accepts an optional table only when one is already assigned and otherwise requires one.
- P07 corrective handoff (2026-08-31, reservation status access): public creation now returns one opaque `access_token` in addition to the existing non-contact reservation snapshot. Store this raw token only in the diner's local secure context; Chowly persists only `SHA-256(access_token)` in `reservations.public_access_token_hash`. P11 must retrieve a later public status through `GET /api/v1/public/reservations/status/{access_token}` and must never construct a status URL from reservation ID or phone number. The status response is `ReservationPublicOut` (no `access_token`, customer name, phone, or notes). Unknown, malformed, ID, and phone-as-token lookups all return generic `404 {"detail":"Reservation not found."}`. Staff queues remain the sole source of contact information and stay protected by assigned-location waiter/manager authorization. Alembic revision `b3c6e0d718f2` follows `a14c29d40b7e`; historic rows get irretrievable random digests, so no status capability can be fabricated for them.

- P07 state/event contract: allowed transitions are `REQUESTED -> CONFIRMED|REJECTED|CANCELLED` and `CONFIRMED -> SEATED|CANCELLED`; all other transitions return conflict. Each staff transition appends one immutable `AuditEvent` with actor, reason/note, before/after data, and timestamp. `reservation.changed` is staged post-commit on separate assigned-location MANAGER and WAITER channels and deliberately contains no customer contact or private note. A seated reservation points to its explicitly selected table and customer but does not mutate table activity or create/merge an order; accepted orders remain the only path that opens table visits.
- P08 feedback route contract: application composition must mount `app.routers.feedback.router`. Public item ratings, order ratings, and complaints use `/api/v1/public/orders/{order_id}/{ratings/items|ratings/order|complaints}` and require the raw order-link token in `X-Order-Access-Token` (or the receipt-link `access_token` query parameter); only its SHA-256 hash exists in SQL. A missing, guessed, or mismatched order/token pair is non-enumerating. Feedback is accepted for `SERVED` and `PAID` orders, and item complaints reference a same-order `ItemRating`, from which the line is derived.
- P08 complaint privacy contract: application composition must expose manager routes from `app.routers.feedback.router` at `/api/v1/staff/locations/{location_id}/complaints`. `MANAGER` plus explicit location assignment is required before list/detail/acknowledge/resolve; waiter, chef, bartender, tenant-owner, foreign-tenant, and guessed-location access cannot retrieve complaint content. Score 1-2 responses contain an optional prompt only and never auto-create a complaint. Acknowledgement and resolution each append actor/timestamped immutable audit events; resolution/dismissal requires a note.
- P08 retention contract: application composition must mount `app.routers.retention.router`. Tenant owners read/update `/api/v1/staff/tenant/retention`; 1-120 days takes effect directly, while values above 120 remain pending and do not alter the effective policy until a platform administrator calls `/api/v1/platform/tenants/{tenant_id}/retention/approve`. `app.retention.run_retention_cleanup` is the late-bound P03 worker adapter. Cleanup anonymizes an expired tenant visibility record in place, leaves financial orders/amounts/statuses intact, and anonymizes the global Customer only when no other tenant retains an unpurged visibility record. Tenant customer-history/contact consumers must scope through `CustomerTenantRecord` and exclude `purged_at IS NOT NULL`; direct global-Customer joins are not a tenant visibility grant.
- P10/P02 auth contract: the client now consumes P02's credentialed HttpOnly-cookie session via `GET /api/v1/staff/auth/session`, `POST /api/v1/staff/auth/login`, `POST /api/v1/staff/auth/logout`, and `POST /api/v1/staff/auth/active-location`; role/location authority comes only from that authenticated session payload.
- P10 offline contract: IndexedDB `chowly-web` schema version 1 has `snapshots` and `outbox` stores. Public snapshots strip contact, email, and access-token fields. Only `SET_WAIT_TIME` and `MARK_PREP_LINE_READY` are queueable; acceptance, service, cancellation, transfer, payments, cash, refunds, QR regeneration, and complaint resolution remain online-only. Replay uses `Idempotency-Key`; 409/412 become human-visible conflicts and other failures remain pending.
- P10 client liveness contract: the frontend follows P03's version 1 role-scoped/public-order channel envelope, deduplicates channel-local sequence numbers, refreshes the REST snapshot on gaps, polls until WebSocket recovery, answers heartbeats, and treats 4401/4403 as terminal authorization failures.
- P10 service-worker contract: `chowly-static-v2` uses stale-while-revalidate only for same-origin Next static assets, icons, and the manifest. Navigations are network-first with `/offline` fallback. `/api/` and Authorization-bearing requests are network-only and never enter Cache Storage.
- P04 schema correction: authorized P04 ownership exception added normalized `menu_categories` and explicit `menu_items.category_id` / `menu_items.queue_destination` through Alembic revision `a14c29d40b7e` after `48f961b063ff`. The migration backfills deterministic UUID5 category IDs portably on SQLite/PostgreSQL, derives existing FOOD to KITCHEN and DRINK to BAR, and makes both new columns constrained/non-null in the migrated database. Direct `Base.metadata.create_all` keeps `category_id` nullable only for pre-P04 legacy/P01 fixture compatibility; P04 HTTP writes always require a scoped active category. Location menu projections are read-only while the category relationship owns writable composite item scope; mapper configuration is warning-free and relationship persistence is tested.
- P04 pricing contract: `app.pricing_service.price_breakdown` uses `Decimal` and `ROUND_HALF_UP` at NGN 0.01 precision. It separately snapshots item subtotal, modifier subtotal, VAT, service charge, and all-in total. `validate_menu_selection` rejects duplicates, foreign IDs, unavailable items/options/categories, and modifier-group min/max violations before an order path may snapshot a line.
- P04 QR contract: `app.qr_service.issue_table_qr` issues one HMAC-unpredictable token per table and location-local calendar day, stores only SHA-256, reconstructs the digital presentation from the opaque row ID plus server secret, and expires it at the next local midnight. Forced regeneration invalidates every active predecessor before insert, adds `TABLE_QR_REGENERATED`, and publishes `table.changed` after SQL commit. Public lookup is hash-based and non-enumerating; invalidated/guessed tokens return 404 and elapsed local-day tokens return 410.
- P04 route contract: export `locations_router`, `menu_router`, and `tables_router` from `app.routers`. Staff APIs live under `/api/v1/staff/locations`; public QR menu/selection APIs are `GET /api/v1/public/tables/{qr_token}` and `POST /api/v1/public/tables/{qr_token}/menu/validate`. P05 must call the pricing/selection service rather than reimplement modifier or tax checks.
- P05 public order contract: `POST /api/v1/public/tables/{qr_token}/orders` always creates a distinct order and required Customer/tenant-visibility record from name and normalized phone, with optional email and no diner account flow. It returns the raw order-link token exactly once while SQL stores only SHA-256. `GET /api/v1/public/orders/{order_id}`, preacceptance `/service-mode`, `/cancel`, and `/realtime-grant` require that token in `X-Order-Access-Token` or `access_token`; feedback and future P06 receipt/payment routes share the same hash-only order-link contract. Public payloads expose aggregate status, the customer-safe `cancellation_reason` after cancellation, and never individual preparation progress, staff identity, customer contact, or audit metadata. The persisted order cancellation reason is therefore customer-safe copy; actor identity and full before/after details remain staff-timeline-only.
- P05 staff/prep contract: authenticated assigned waiters/managers operate `/api/v1/staff/orders/**`; assigned chefs/bartenders operate `/api/v1/staff/prep` and `/api/v1/staff/lines/{line_id}/{claim|ready}`. Acceptance assigns an eligible waiter owner and opens/reuses a Table Visit. Manager reassignment, owner/manager transfer, pre-claim amendment, reasoned cancellation, manual order creation, wait-time selection, and service are explicit audited transitions. Claim is an atomic conditional SQL update; a claimed line is waiter-locked and only a manager may cancel it with an explicit reason.
